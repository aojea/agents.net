# Stakeholder Review (September 2026): Simulated Personas and Disposition

**Status:** Informative record  
**Date:** September 17, 2026  
**Reviewed revision:** the specification in the specification as it stood in the repository README on that date and the reference implementation at commit `338f480`  
**Outputs:** the [specification](../spec/draft/index.md), the [roadmap](roadmap.md), and the [conformance suite](../conformance/README.md)

## 1. Method

Nine reviews were produced by independent, read-only agent sessions, each
instructed to argue from the position of a named organization or product
family. No employee of any named organization participated. The reviews
represent plausible technical positions derived from public product behavior;
they are not statements by those organizations.

Each review classified its claims as VERIFIED (quoted from the specification or
code) or INFERRED. Before adoption, every VERIFIED claim about the reference
implementation was rechecked against the source. Claims that failed the recheck
are recorded in Section 4 and were not carried into the design.

| --- | --- |

## 2. Consolidated Findings

Findings raised by more than one persona, in decreasing frequency:

1. No portable policy format. Policy exists only as reference command flags. (P1, P3, P4, P7, P8)
2. Failure signaling uses a private header. `Boundary-Reason` is neither registered nor structured; RFC 9209 `Proxy-Status` covers the same purpose. (P1, P6, P9)
3. No first-class explicit-proxy adapter. Hosts without TUN or network namespaces (macOS, Windows) can confine proxy-aware clients but cannot conform. (P1, P2, P4)
4. Shared boundary process serving several dedicated listeners lacks a conformance statement. (P3, P5, P7)
5. Hostname patterns. Only exact names and `*` are accepted; suffix patterns are used by every reviewed product. (P1, P4, P7)
6. Audit record fields are implementation-defined. (P4, P6, P7)
7. Ingress handshake is a deployment convention. (P2, P7, P8)
8. Applications cannot distinguish a policy denial from an unreachable destination. (P8; latency of refusal also noted by P3)
9. The HTTP/1.1 reference client accepts only status 200 for CONNECT; RFC 9110 permits any 2xx. Interim 1xx responses are not addressed. (P4, P9)
10. Snapshot and restore of a guest with cached synthetic addresses is stated as a requirement without a mechanism. (P5)
11. Dialing rules after resolution (alternate family, retry, static mapping, proxy chain) are stated but not enumerated. (P6)
12. A conformance harness must supply its own resolver and upstream so that vendors can run it in CI without network access. (P6, P7)

## 4. Claims Not Carried Forward

The following were asserted as findings and did not survive rechecking:

- "Namespace rules remain after an unplanned proxy exit and can leak traffic." The specification already required the controller to destroy the namespace and to start a fresh one on restart; the workload has no external interface in that namespace.
- "Metadata and private addresses are not denied in the baseline." The egress interface already required explicit authorization; the reference denies loopback, private, link-local, and the listed special-purpose ranges unless listed. The specification now states the table ([wire.md §5.1](../spec/draft/wire.md#51-special-purpose-addresses)), not a new rule.
- "An allowed name resolving to loopback reaches the boundary's own listeners." The reference denies loopback results unless listed; the specification states the requirement.
- "The boundary must recognize synthetic names." Adapters never send synthetic addresses as names; they send the reversed hostname or, on a reverse miss, the literal address, which the boundary denies as non-public.
- "Envoy dials resolved addresses without per-address policy." Not tested here; recorded as a harness question, not a finding.
- Line-number citations produced by the reviews were not used; quoted text was rechecked by search.

## 5. Verified Defects and Gaps in the Reference

| Item | Evidence | Disposition |
| --- | --- | --- |
| HTTP/1.1 client treats only 200 as success | [connect.go](../sdk/pkg/tun2connect/connect.go): `if resp.StatusCode != http.StatusOK`; the HTTP/2 client accepts 200-299 | Closed: any 2xx is success; unit-tested; suite case A-PKT-09 |
| HTTP/1.1 client reads one response and does not skip 1xx interim responses | `roundTrip` returns the first response read | Closed: interim responses are skipped up to a bound; A-PKT-10 |
| Boundary does not check `SETTINGS_ENABLE_CONNECT_PROTOCOL` before accepting extended CONNECT | Delegated to `golang.org/x/net/http2`, which rejects `:protocol` when the setting is disabled | Documented; B-H2-05 |
| No suffix name patterns | `parseAllow` accepts exact names or `*` | Closed: descriptor `suffix` rules; B-CORE-54..56 |
| Policy is command-line only | `main()` flags | Closed: the boundary takes `-policy <descriptor.json>` and nothing else |
| Denial signaling was a private `Boundary-Reason` header | `h1Responder.deny`, `h2Responder.deny` | Closed: `Proxy-Status` in the reference boundary, clients, demo, and tests; B-CORE-53 |
| No audit record for requests refused with 405 `connect-only` | `serve()` default branch calls `deny` without `audit` | Closed; B-CORE-24, 25, 28 |
| `-allow-ip` authorizes both literals and resolution results | `listedAddress` is consulted for both paths | Closed: literal rules and `resolved_addresses` are separate in the descriptor; B-CORE-45 |

The [harness run](../conformance/README.md#7-running-the-harness) against the reference after these changes: every automated `boundary-core` case passes.
